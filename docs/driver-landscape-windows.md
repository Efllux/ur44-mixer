# WinUSB can drive the UR44, but not match macOS

**An own user-mode Windows driver for the UR44 in vendor mode (0499:150e) is buildable today, but the evidence says it will not reach the macOS driver's ~1.6–1.7 ms analog round trip.** Two public Rust projects already stream isochronous USB audio through Microsoft-signed WinUSB with an in-process ASIO DLL, so a kernel driver, an EV certificate and test-signing are not needed for ASIO. They also expose the limits. WinUSB completes isochronous transfers at best every 1 ms ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winusb/nf-winusb-winusb_writeisochpipeasap)), and its write calls cannot set per-packet lengths. That second limit collides with the UR44's implicit-feedback packet sizing, and it is the one make-or-break unknown. The best published Windows result for the family is **3.67 ms at 32 samples/44.1 kHz** (UR44C, current Yamaha driver), against a Mac driver whose non-buffer overhead is at most about 1.1 ms ([DAWbench](https://dawbench.com/images/DAWbench%20LLP%20Database-March-2026-Public.pdf)). Our unmeasured estimate for a WinUSB design is **about 3–5 ms at 32 samples/48 kHz**, so the realistic goal is parity with Yamaha's own Windows driver, not with the Mac driver. A system-audio endpoint (WASAPI) cannot be made in user mode at all; it needs a signed kernel miniport, so it should be an optional later phase. Decompiling Yamaha's driver adds little. The black-box route (USB capture, ASIO call logging) is lawful in the Netherlands regardless of the EULA, while decompilation is legally narrow and incompatible with publishing the result under MIT. Licence-wise, an MIT core plus a separate GPL-3.0 ASIO adapter DLL is the cleanest layout. Nothing here is legal advice, and no hardware was tested.

Evidence conventions follow the macOS edition, [driver-landscape.md](driver-landscape.md) (2026-11-07). **P** is the GitHub `pushed_at` date; **D** is a dated document; **V** was checked at the source in this research without a reliable date. "Rel." is relevance, 1 to 5, as in that report. Items marked *inference* are the researchers' reasoning, not published facts. Where notes disagree, the final notes were preferred, and unresolved conflicts are listed in the contradictions register after the gaps section.

## Summary: ten most valuable finds

1. **[RamonWide/AxeTwoDriver](https://github.com/RamonWide/AxeTwoDriver)**, MIT: the closest match to our device class. It is a high-speed, implicit-feedback, vendor-mode Fractal Axe-Fx II driver in pure Rust over WinUSB. Its crates are `axetwo-usb` (descriptor parsing), `axetwo-win` (the only `unsafe`, WinUSB FFI) and `axetwo-stream` (duplex loop with 1 ms transfers and a 2 ms playback lead). It is directly reusable under MIT, but it was tested on one unit, one PC and 20 s runs, and it lacks MMCSS.
2. **[NazEtner/sd90](https://github.com/NazEtner/sd90)**, GPL-3.0: a Rust ASIO DLL over WinUSB isochronous for a vendor-mode Roland SD-90. It documents the WinUSB-specific traps (one transfer = one packet on OUT, `Offset` is per transfer, EMA-smoothed drift servo, MMCSS on both threads, host quirks). It is a full-speed device, and its "3.38 ms" figure is **not** an ASIO round trip (see section 3).
3. **[WinUsb_WriteIsochPipeAsap](https://learn.microsoft.com/en-us/windows/win32/api/winusb/nf-winusb-winusb_writeisochpipeasap)**: the primary-source constraints. No per-packet length parameter, packets filled to the endpoint maximum per interval, and a 1 ms floor on completion notification.
4. **[AxeTwoDriver-DAW](https://github.com/RamonWide/AxeTwoDriver-DAW)**, GPL-3.0: the licence-split precedent (MIT core, GPL-3.0 ASIO DLL, hand-written IASIO declarations) and a working ASIO adapter that re-blocks 1 ms transfers into host buffers.
5. **[DAWbench LLP database, March 2026](https://dawbench.com/images/DAWbench%20LLP%20Database-March-2026-Public.pdf)**: the only large published Windows round-trip dataset, including the UR44C, the original UR44 (old Win7 driver only) and the best USB2 reference (MOTU M2).
6. **[Steinberg ASIO SDK 2.3.4](https://download.steinberg.net/sdk_downloads/ASIO-SDK_2.3.4_2025-10-15.zip)**: dual-licensed (Steinberg proprietary or GPLv3) since October 2025. This changes the licensing picture for an open project, and it also supplies the registry layout (`register.cpp`) and the `getLatencies`/`outputReady` semantics.
7. **[WinUsb_GetCurrentFrameNumberAndQpc](https://learn.microsoft.com/en-us/windows/win32/api/winusb/nf-winusb-winusb_getcurrentframenumberandqpc)**: a stack-provided microframe-to-QPC mapping with a predicted-accuracy field. It is the Windows analogue of the macOS frame/host-time anchor.
8. **[Microsoft's April 2026 kernel-trust change](https://techcommunity.microsoft.com/blog/windows-itpro-blog/advancing-windows-driver-security-removing-trust-for-the-cross-signed-driver-pro/4504818)**: why any kernel component (system-audio bridge, UsbDk, old Scream-style builds) is now a signing problem on Windows 11 24H2 and later.
9. **[Oblique RTL Utility v1.0.14](https://dev.oblique-audio.com/rtl-utility.php)**: runs on Windows (x64, ARM64) with ASIO and a CLI. It is the same tool as on the Mac, so results compare across platforms.
10. **[Directive 2009/24/EC Arts. 5(3), 6, 8](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32009L0024)** with [Auteurswet 45l/45m](https://wetten.overheid.nl/BWBR0001886/): black-box study cannot be prohibited by contract, and decompilation is allowed only under narrow conditions that exclude reuse in a similar program.

## 1. WinUSB isochronous transport: what the API allows

The transport result that matters is the mirror image of the macOS one. On macOS the obstacle was libusb's four-frame lead; on Windows it is the API shape itself. WinUSB isochronous I/O has existed since Windows 8.1 and works only when Microsoft's `Winusb.sys` is the device's function driver. The flow is `WinUsb_QueryPipeEx`, `RegisterIsochBuffer`, then `Read/WriteIsochPipeAsap` (stack picks the start frame, `ContinueStream` chains transfers) or the explicit-frame variants, completed through OVERLAPPED ([Microsoft guide](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/getting-set-up-to-use-windows-devices-usb)). Transfers are whole 1 ms frames (8 microframes at high speed). Microsoft states that "the lowest latency notification to an application or driver is 1ms intervals" ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winusb/nf-winusb-winusb_writeisochpipeasap)). The documented explicit-frame sample leads by five frames (`frameNumber + 5`), which is a "safe" margin and not a stated minimum ([Microsoft guide](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/getting-set-up-to-use-windows-devices-usb)). The kernel URB rules beneath it discard any packet whose frame is already past, and the URB `StartFrame` counts 1 ms frames, not microframes ([Microsoft URB page](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/transfer-data-to-isochronous-endpoints)). The guide's "250-microseconds microframes" is a Microsoft typo; the URB page's 125 µs is right.

**The headline constraint is OUT packet sizing.** `WinUsb_WriteIsochPipeAsap` takes `(BufferHandle, Offset, Length, ContinueStream, Overlapped)` and no packet-descriptor array. It "packetizes the transfer buffer so that in each 1ms interval, the host can send the maximum bytes allowed per interval" ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winusb/nf-winusb-winusb_writeisochpipeasap)). The explicit-frame `WinUsb_WriteIsochPipe` has the same signature shape, and the libusb Windows backend enforces the same limit: OUT packets must be contiguous, each equal to the endpoint maximum except a short last one ([libusb windows_winusb.c](https://github.com/libusb/libusb/blob/master/libusb/os/windows_winusb.c)). By contrast, the kernel URB interface ignores `IsoPacket[i].Length` on OUT and takes sizes from `Offset` deltas, so kernel clients can send variable packets ([Microsoft URB page](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/transfer-data-to-isochronous-endpoints)). The macOS engine sizes each OUT packet from the matching capture packet (implicit feedback), and the UR44's OUT endpoint must allow one sample more than nominal. Under WinUSB the device would therefore see packets filled to the maximum. AxeTwoDriver documents exactly this behaviour: 48 frames per millisecond go out "as six packets of 7 frames and one of 6, not as eight packets of 6", with correct totals and no reported errors ([AxeTwoDriver architecture](https://github.com/RamonWide/AxeTwoDriver/blob/main/docs/architecture.md)). sd90 sidesteps the problem on a full-speed device by sending one packet per transfer, 1000 transfers per second, with 47/48/49-sample lengths chosen by a servo ([sd90 README](https://github.com/NazEtner/sd90)). That trick is unavailable at high speed because a transfer is at least one 8-packet frame. Whether the UR44 tolerates the bursty distribution is unknown and is gate G2 below.

Two further transport facts shape the design. Starting a stream without `ContinueStream` costs about five empty frames, per the libusb maintainer's profiling comment, so the engine must keep transfers chained and refill ahead of the stream ([libusb windows_winusb.c](https://github.com/libusb/libusb/blob/master/libusb/os/windows_winusb.c)). And a WinUSB device node permits a single open ("WinUSB does not support multiple concurrent applications"), which matters for a composite device that also needs a mixer-control path ([libusb wiki](https://github.com/libusb/libusb/wiki/Windows)). usbccgp splits composite devices into `MI_xx` children that can each be bound to WinUSB (libwdi's `[&MI_##]` naming supports this), so audio and mixer interfaces in two processes should work, but no source verifies it for the UR44 ([libwdi FAQ](https://github.com/pbatard/libwdi/wiki/FAQ)).

## 2. Existing ASIO drivers and the user-mode isochronous precedent

No mature open Windows user-mode USB ASIO driver for a pro interface exists. The public record contains three Rust projects, all created between July and October 2026, each by one author, with one to three stars and no published round-trip measurement, and a GitHub search for further WinUSB or libusb ASIO drivers found only the old C++ `audioxtreamer`. Both vendor-mode projects carry agent-instruction files (`AGENTS.md`), which suggests AI-assisted, weeks-old code bases; treat their claims as unreviewed (inference). They are architecture references, not dependencies, with one exception: AxeTwoDriver's MIT crates are plausible starting code because the Axe-Fx II is also a high-speed device with implicit feedback.

sd90 and AxeTwoDriver independently converged on the same engine shape: one worker thread owns the WinUSB handle (the handle is not `Send`), IN transfers are queued deep, OUT is driven from what IN delivers (capture-slaved, as in the Linux implicit-feedback practice), and a ring buffer decouples USB cadence from the ASIO block size. AxeTwoDriver keeps 8 capture transfers in flight, each 1 ms, queues an equal number of playback frames per completion, and defaults to a 2 ms playback lead with 6 spare slots ([AxeTwoDriver architecture](https://github.com/RamonWide/AxeTwoDriver/blob/main/docs/architecture.md)). sd90's drift servo failed when it ran on the raw ring fill (amplitude jumps about once per second) and worked with an exponential moving average on a 1 s time constant, with zero jumps in 15 s ([sd90 README](https://github.com/NazEtner/sd90)). Hosts add quirks that a clean-room ASIO author will meet: SONAR stops if outputs are zero, hosts pass the CLSID as the IID to `QueryInterface`, and Windows `ASIOSamples`/`ASIOTimeStamp` are `{hi, lo}` pairs; on x64 plain `extern "system"` vtables match IASIO ([sd90 README](https://github.com/NazEtner/sd90)). The ASIO interface itself helps latency in one specific way: if the driver returns `ASE_OK` from `outputReady()`, the host signals output-complete and the driver can convert and submit the next USB buffer immediately, which removes one block of output latency ([ASIO SDK](https://github.com/langlauf/asiosdk), mirror of 2.3.4).

## 3. Latency and clock evidence: why parity with the Mac driver is unlikely

**The sd90 figure is not an ASIO round trip.** The 3.38 ms (1 packet per transfer) and 7.33 ms (8 packets) numbers measure the EDIROL SD-90's own response: frames between a scheduled MIDI note and its onset appearing in the capture stream, on a full-speed device. The 4 ms difference is half the 8 ms update interval. The README publishes no ASIO round-trip number, and its ASIO default stays at 8 packets per transfer ([sd90 README](https://github.com/NazEtner/sd90)). What it does prove is that **transfer granularity becomes clock granularity**: moving from 8 ms to 1 ms completions cut timing jitter from about 5.2 ms to 0.13 ms. That finding applies directly to the frame/QPC mapping on Windows.

**The Windows reference data.** The DAWbench database measures analog loopback with Oblique's RTL Utility at 44.1 kHz only. "Overhead" below is round trip minus two buffers (our arithmetic at 44.1 kHz; the 32-sample buffer is 0.726 ms).

Source for all rows: [DAWbench LLP database, March 2026](https://dawbench.com/images/DAWbench%20LLP%20Database-March-2026-Public.pdf). The author's own caution applies: panel buffer settings are often "little more than window dressings" and one unit's 64-sample setting ranged from under 4 ms to over 12 ms ([DAWbench article](https://dawbench.substack.com/p/audio-interface-low-latency-performance)). A forum report of 14.35 ms for the UR44 at 128 samples/44.1 kHz matches the Win7 row ([Steinberg forum](https://forums.steinberg.net/t/what-is-your-roundtrip-latency-with-the-ur44/649585)). Nobody has remeasured the original UR44 on a current Yamaha driver under Windows 10/11, so the UR44C is the best proxy, with a different, USB3-capable unit.

**Normalising to the Mac result.** The Mac round trip is 2 × buffer plus about 0.55–0.60 ms of UR44 digital loop plus margins, so at 1.6–1.7 ms the non-buffer overhead is at most about 1.1 ms (inference from the project's own figures; the exact Mac buffer sizes per rate were not supplied, so a precise table cannot be finished). The best Windows vendor USB drivers carry 1.7–2.2 ms. The Mac driver's overhead is therefore roughly half of the best Windows USB drivers, and the gap widens at 96 and 192 kHz because buffers cost less time while the fixed overhead remains. DAWbench has no data above 44.1 kHz.

**Why WinUSB probably sits at or above the vendor drivers.** Completions arrive in 1 ms quanta, at least two transfers must be in flight per direction, output must be queued at least a frame ahead of the wire, and input becomes visible only at a 1 ms completion plus thread wake-up. The estimate is **RTL ≈ 2 × buffer + 2–4 ms USB lead and quantisation + about 0.6 ms UR44 loop, which is 3–5 ms at 32 samples/48 kHz** (inference, unmeasured, in the earlier researcher's words "must be measured"). Two points soften this. First, even a kernel driver on Microsoft's stack submits isochronous URBs in 1 ms units at interval 1, because packets per URB must be a multiple of 8 ([Microsoft URB page](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/transfer-data-to-isochronous-endpoints)); the kernel advantage is per-packet sizing and tunable lead, not sub-millisecond transfers. That is consistent with Yamaha's own kernel driver landing at about 2.2 ms overhead, which a good user-mode design could approach. Second, the macOS driver's edge comes from IOUSBHost mechanisms (per-microframe scanning of queued transfers, as in the QuadCaptureMac design described in the macOS report) with no documented Windows equivalent. An untested hypothesis worth one afternoon on the bench is whether a registered isochronous buffer, being user memory, shows IN data before the transfer completes; the documentation does not promise it.

**Clock mapping.** `WinUsb_GetCurrentFrameNumberAndQpc` (Windows 10+) fills a structure with a QPC value for a given frame and microframe, `PredictedAccuracyInMicroSeconds`, `CurrentGenerationID` and the xHCI hardware frame/microframe read from MFINDEX ([Microsoft struct](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/usbioctl/ns-usbioctl-_usb_frame_number_and_qpc_for_time_sync_information)). This is the Windows counterpart of the macOS frame-to-host-time anchor, and the generation ID lets the engine detect discontinuities after sleep or controller resets. Typical accuracy and generation-change frequency are undocumented. The ASIO side has its own convention: the sample-position/time-stamp pair must refer to the current block, the first block after `start()` reports position zero, and the system time on Windows "must be derived from timeGetTime()" ([rtaudio asio.h copy](https://github.com/thestk/rtaudio/blob/master/include/asio.h)). Converting a QPC-based estimate into the `timeGetTime` epoch with a fixed offset is our inference. At 44.1 kHz the implicit-feedback pattern is 5/6 frames per microframe (44.1 frames per ms), so OUT sizes must copy observed IN sizes as on Linux, never be computed independently. The macOS report's DLL references (SPA `dll.h`, Adriaensen's paper) carry over unchanged.

**Scheduling and power on Windows.** Use MMCSS "Pro Audio" on both the USB completion thread and the ASIO callback thread, as sd90 does ([MMCSS](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)). Opt the process out of EcoQoS (`ProcessPowerThrottling` with `StateMask = 0`) and honour timer requests ([SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)). The ASIO callback runs inside the DAW process, so users on Intel hybrid CPUs may need `powercfg /powerthrottling disable /path "<exe>"`, which Steinberg documents for Cubase ([Steinberg](https://www.steinberg.help/r/windows-dropouts-on-intel-hybrid-architecture-cpus-with-cubase/nuendo-running-in-background)). A user-mode completion thread is exposed to scheduler risk that a kernel DPC is not (inference). No source documents whether MMCSS registration pins threads to P-cores, no LatencyMon pass/fail threshold in microseconds exists, and nobody has published a CPU-cost comparison of IOCP, event and polling for WinUSB isochronous. Expect at least 1000 completions per second per direction no matter what.

## 4. System audio, signing and installation: where the kernel reappears

**A system-audio endpoint cannot be created in user mode.** Windows endpoints come from WaveRT/PortCls or ACX miniports; ACX is built on KMDF, and Microsoft's virtual-audio samples (SysVAD, SimpleAudioSample, SdcaVad) are kernel drivers ([ACX overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/acx-audio-class-extensions-overview), [Low Latency Audio](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)). An OSR answer says this "cannot be done in user-mode" ([OSR](https://community.osr.com/t/seeking-assistance-how-to-create-virtual-input-and-output-devices-in-windows-11/59143)), and AxeTwoDriver states the same and does not plan it ([README](https://github.com/RamonWide/AxeTwoDriver)). No user-mode endpoint API was found in Windows 11 24H2 through 26H1, though absence is "not found", not confirmed. The Windows analogue of the macOS AudioServerPlugIn is therefore a SysVAD- or ACX-derived kernel miniport that reads and writes a shared-memory ring, which the user-mode engine fills and drains. It would also be slower than ASIO: SysVAD's low-latency example declares a 2 ms minimum period, and the shared-mode engine adds about 1.3 ms on render ([Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)).

**Signing economics.** Microsoft's April 2026 update removed default kernel trust for the deprecated cross-signed program on Windows 11 24H2, 25H2 and 26H1 and Server 2025; only WHCP-signed kernel drivers load by default, with an allow-list and a custom App Control policy as exceptions ([Microsoft](https://techcommunity.microsoft.com/blog/windows-itpro-blog/advancing-windows-driver-security-removing-trust-for-the-cross-signed-driver-pro/4504818)). Attestation signing needs a Hardware Developer Program registration, an EV code-signing certificate, a Microsoft Entra global administrator and a legal contact authorised to sign agreements; the page describes organisations and neither offers nor excludes individuals ([registration](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/hardware-program-register), [attestation](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/code-signing-attestation)). Attested drivers cannot go to Windows Update, and the section is now headed "for testing scenarios" ([Driver Signing Options](https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/driver-signing-offerings)); Microsoft's page says nothing about distributing them elsewhere. EV certificates cost roughly $250–700 a year on vendor price lists, with a cap of about 458–460 days of validity since early 2026 (sources disagree on the exact figure) ([SSL.com](https://www.ssl.com/products/software-integrity/code-signing/ev/)). Test-signing needs Secure Boot off per the Scream README and shows a watermark; the anti-cheat consequences are unverified anecdote. WinUSB avoids all of this because `winusb.sys` is already Microsoft-signed, which is why sd90 and AxeTwoDriver chose it ([sd90 README](https://github.com/NazEtner/sd90)).

**Binding WinUSB to the UR44.** Microsoft's route is an INF (`Include=winusb.inf`, `Needs=WINUSB.NT`, a `DeviceInterfaceGUIDs` entry) with a signed catalog, which "is required to install WinUSB on Windows" ([Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/winusb-installation)). The UR44 firmware cannot supply Microsoft OS descriptors, so an INF is unavoidable. libwdi and Zadig generate a self-signed catalog per install, delete the private key and put the certificate into LocalMachine Root and TrustedPublisher ([libwdi FAQ](https://github.com/pbatard/libwdi/wiki/FAQ)). That path broke on Windows 11 Insider builds in 2021 and was reported working on release builds ([OSR](https://community.osr.com/t/windows-11-and-alternative-driver-installation-method-in-libwdi/57493)). Recent Windows 11 failures appear in forums, with causes unverified ([Electro-Smith](https://forum.electro-smith.com/t/daisy-seed-not-recognized-by-windows-11/9090)), and no official statement says that 24H2 or 25H2 rejects self-signed catalogs for in-box drivers. Memory Integrity governs kernel binaries and Smart App Control governs user-mode executables, so the INF path should be unaffected by the first and an unsigned helper executable might be hit by the second (inference). AxeTwoDriver's installer selects `winusb.inf` for the device node and adds no certificate at all, and its binary is unsigned (SmartScreen warns) ([AxeTwoDriver docs](https://github.com/RamonWide/AxeTwoDriver/blob/main/docs/architecture.md)). That route is the one to test first.

Yamaha's own driver complicates binding. Windows 11 sometimes binds its generic "USB Audio 2.0" class driver to the UR44, and the community fix is a manual "Let me pick" driver selection that may need repeating after a port change ([Steinberg forum](https://forums.steinberg.net/t/ur44-driver-fix/1033264)). The project's INF must outrank both Yamaha's and the in-box driver for the audio interfaces, and installing it disables the Yamaha ASIO driver on those interfaces.

**Microsoft's own low-latency stack does not help.** The new in-box UAC2 driver with ASIO (built with Qualcomm and Yamaha, MIT, [repo](https://github.com/microsoft/low-latency-audio)) targets UAC2 devices, has no public release ("There is no public release of the driver, yet") and says nothing about vendor-class devices. Microsoft expected a Canary preview "in 2026" ([Windows Music Dev blog, 2025-11-12](https://devblogs.microsoft.com/windows-music-dev/fall-2025-windows-musician-technology-and-arm64-update/)). Whether a preview has shipped as of this writing is unconfirmed. Its `uac2-asio` source is a good design reference, and Microsoft's README requires a Steinberg agreement to build it.

## 5. Yamaha's Windows driver, public protocol work, and the Linux claim

**Official state.** The UR44 is still on Steinberg's hardware download page and not in the "unsupported hardware" archive, but Windows TOOLS is V2.2.2 (2021-07-07, bundling USB Driver V2.0.4 and dspMixFx V2.2.0), while macOS got TOOLS V2.3.0 (2023-02-07) ([Steinberg UR44 downloads](https://download.steinberg.net/downloads/hardware/ur44.html), [unsupported list](https://download.steinberg.net/downloads/downloads-unsupported-hardware.html)). An earlier lead claiming a Windows TOOLS V2.3.0 is therefore wrong; the 639 MB package is the macOS one. The current standalone driver is **Yamaha Steinberg USB Driver V2.1.9 for Windows 10/11 x64** (`YSUSB_V219_Win.zip`, behind Yamaha login), whose Arm list does not include the UR44, so Windows-on-Arm users of the original UR44 have no official driver ([Yamaha](https://usa.yamaha.com/support/updates/yamaha-steinberg-usb-driver-v219-for-win.html)). Support for Steinberg hardware has moved to Yamaha since 2025-04-01 ([Steinberg downloads index](https://download.steinberg.net/downloads/index.html)). The UR44 is effectively in legacy status on Windows, not discontinued. The release notes show what the Windows driver adds over a plain implementation: a Latency Mode setting (2.0.3), a 32-sample ASIO buffer and small-buffer noise fixes (1.10.3), and a firmware requirement of V2.10 or newer ([TOOLS 2.2.2 release notes](https://download.steinberg.net/downloads_hardware/UR44/PC/2.2.2/ReleaseNotes_win.pdf)). Real `.sys` and `.dll` names are unverified (only the INF names `ysusb_w10.inf` and `ysusb.inf` appear in third-party listings), so none should be cited.

**Protocol work to reuse.** The USB-level protocol is shared with the macOS driver, so Windows needs descriptors and captures, not new reverse engineering. The best open material is unchanged from the macOS report: [askoriy/urcontrol](https://github.com/askoriy/urcontrol) (MIT, UR44C SysEx plus a Wireshark Lua dissector; the second MIDI port "becomes hidden once the official drivers are installed"; no capture files published), Cyrus Harmon's 2014 `0499:150e` quirk and the one public UR44 descriptor dump ([thorhop gist](https://gist.github.com/thorhop/19c6e4a71953d1335b2d), five interfaces). No Windows libusb or WinUSB experiments with any UR device, no public pcaps and no decompilation write-ups were found. urcontrol's capture recipe (Windows guest with the official drivers in a VM, device passed through, usbmon plus Wireshark) is directly reusable on the original UR44.

**Correction to the macOS report's Linux claim.** The macOS edition said no `0x150e` entry exists in current Linux files. That stands: `quirks-table.h` has an explicit entry for UR22 `0x1509` (`STANDARD_AUDIO(1)`, `(2)`, `MIDI_YAMAHA(3)`, `IGNORE(4)`) but none for `0x150e`, and `quirks.c` sets `GENERIC_IMPLICIT_FB` for UR22 but not UR44 ([quirks-table.h](https://github.com/torvalds/linux/blob/master/sound/usb/quirks-table.h), [quirks.c](https://github.com/torvalds/linux/blob/master/sound/usb/quirks.c)). What was missing is the nuance. A **Yamaha vendor-wide catch-all** (VID `0x0499` plus vendor-specific interface class, `QUIRK_AUTODETECT`, around lines 459–468 of the table) exists, so Linux does attempt to autodetect the UR44's vendor-class interfaces, and `create_autodetect_quirk` falls back to `create_yamaha_midi_quirk`. "No explicit quirk" therefore does not mean "unsupported", and the macOS report's recommendation to upstream a minimal Linux quirk should first test what autodetection already does. No Windows-side equivalent of any of this exists.

## 6. Is decompiling Yamaha's Windows driver useful or legal?

**It is not useful enough to justify the risk.** What the Windows driver contains that the macOS work may lack (Latency Mode, a 32-sample buffer, small-buffer noise fixes, Modern Standby resume handling) is observable by black-box measurement: log `getLatencies` and `getBufferSize` from a host at each buffer size and Latency Mode, and capture the USB traffic per mode with USBPcap, which shows how much is queued ahead and how many packets each URB carries ([release notes](https://download.steinberg.net/downloads_hardware/UR44/PC/2.2.2/ReleaseNotes_win.pdf)). The Windows-only work (INF priority against Yamaha's INF and `usbaudio2.sys`, signing, multi-client behaviour, power management) is not in the Yamaha binary in any case. The USB protocol is already known from the macOS effort, which also weakens any claim that decompilation is "indispensable".

**The Dutch and EU legal position, separated from commentary.** Yamaha's EULA s.2 forbids "reverse engineering, disassembly, decompilation" and derivative works, and s.10 selects Japanese law and the Tokyo District Court ([Yamaha](https://usa.yamaha.com/support/updates/yamaha-steinberg-usb-driver-v219-for-win.html)). Against that, Directive 2009/24/EC provides three rules ([EUR-Lex](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32009L0024)). Art. 5(3) lets a lawful user observe, study and test how a program works while running it. Art. 6 permits decompilation only if indispensable to achieve interoperability of an independently created program, if the information was not readily available, and if confined to the necessary parts; Art. 6(2) bars using the result for other goals, passing it on beyond need, or building a program "substantially similar in its expression". Art. 8 makes contract terms contrary to Art. 6 and Art. 5(3) null and void. The Dutch Auteurswet implements these as Art. 45l (study) and Art. 45m (decompilation), with no "unless agreed" carve-out in either, whereas Art. 45j begins "Tenzij anders is overeengekomen" for ordinary use ([wetten.overheid.nl](https://wetten.overheid.nl/BWBR0001886/)). The CJEU held that functionality, programming languages and data-file formats are not protected expression and that a licensee may observe, study and test under Art. 5(3), while copying manual text can infringe ([C-406/10 SAS Institute](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:62010CJ0406)). One Dutch IT-law commentary says Arts. 45j–45m are mandatory, though its article numbering is internally inconsistent ([FLIB](https://www.flib.nl/en/expertise/it-law/copyright-on-software/)). The Dutch legislative history could not be read, and no Dutch case law was located.

**Consequences for the project (inference, not legal advice).** Black-box study, meaning USB captures with the official driver running and ASIO call logging, falls under Art. 5(3)/45l and cannot be contracted away; the Japanese governing-law clause probably does not change that for an EU user, but no commentary was found to support the conflict-of-laws point. Decompilation under Art. 6/45m is defensible only for specific, still-unknown items (for example DSP or mixer register semantics that capture cannot reveal), only for the parts needed, and the output may not be published or used to build a similar program. That rules out committing decompiler output, pseudo-code or driver tables to an MIT repository, because calling the repository MIT does not clean copied Yamaha expression. Whether UR44 interoperability information is "readily available" is a factual question for counsel, and US enforceability of anti-reverse-engineering clauses (the earlier researcher cited *Bowers v. Baystate* and *Sega v. Accolade* from memory) was not verified. If decompilation is ever needed, use a clean-room split (one person writes a dated functional specification, another implements from it only), keep records of the interoperability purpose, and take Dutch legal advice first. Do not redistribute Yamaha driver binaries or firmware images, and do not trigger firmware-update paths from the open driver.

## 7. Tooling, measurement, Rust and CI

**Capture.** USBPcap plus Wireshark remains the only practical Windows payload capture, but the project is stale: release 1.5.4.0 is from 2020-05-22, last push 2025-02-09, and an open issue reports a BSOD (opened 2026-03-26) ([USBPcap](https://github.com/desowin/usbpcap)). Its page says it works on Windows 7, 8 and 10 and never mentions Windows 11, so keep a VM or snapshot. It captures URBs, not bus packets: no NAKs, PIDs or timing, and for isochronous transfers each IRP yields two capture packets, so per-microframe timing cannot be derived ([capture limitations](https://desowin.org/usbpcap/capture_limitations.html)). The engine therefore needs its own QPC-stamped log of every isochronous completion, and Microsoft's USB ETW providers (`Microsoft-Windows-USB-USBXHCI`, `-UCX`, `-USBHUB3`) are the right tool for stalls, with no maintained payload viewer ([Microsoft USB ETW](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-event-tracing-for-windows)). `aka.ms/usbtrace` now redirects to a general "buses" tracing folder (`BusesTrace.cmd` with a WPR profile), not the older logman-only script ([busiotools](https://github.com/Microsoft/busiotools/tree/master/usb)).

**Measurement.** Oblique's RTL Utility v1.0.14 (2026-10-25) runs on Windows x64 and ARM64 over ASIO with physical loopback and a CLI with CSV output, and it flags results that disagree with driver-reported latency, so `getLatencies` must be honest ([Oblique](https://dev.oblique-audio.com/rtl-utility.php)). Its 32-bit Windows build is deprecated, so a 32-bit-only ASIO DLL cannot be measured with it. LatencyMon (use the vendor site only; a 2026 blog warns about fake "v8" downloads) and WPA/xperf cover DPC time and context switches, the Windows equivalent of macOS wakeups per second ([Microsoft CPU analysis](https://learn.microsoft.com/en-us/windows-hardware/test/wpt/cpu-analysis)). A Rust loopback harness can drive the ASIO DLL through [cpal](https://github.com/RustAudio/cpal) (`Host::Asio`, Apache-2.0, cpal 0.18.2 with asio-sys 0.4.0), which needs LLVM/Clang and downloads the SDK at build time.

**Rust and COM.** Use direct `windows-sys`/`windows` calls for WinUSB isochronous and a `cdylib` COM in-process server (`DllGetClassObject`, `DllCanUnloadNow`, `DllRegisterServer`, `DllUnregisterServer`) for ASIO. `com-rs` is archived and `intercom` is stale. The SDK's `register.cpp` fixes the registry layout: `HKCR\CLSID\{clsid}\InprocServer32` with `ThreadingModel`, plus `HKLM\SOFTWARE\ASIO\<name>` with `CLSID` and `Description` values ([ASIO SDK 2.3.4](https://download.steinberg.net/sdk_downloads/ASIO-SDK_2.3.4_2025-10-15.zip)). A 32-bit build is a separate DLL registered in the WOW6432Node view and would need an IPC bridge to the 64-bit process that owns the WinUSB handle ([cwASIO README](https://github.com/s13n/cwASIO)); it is low priority. GitHub's windows-2025 runner has Rust, LLVM 20, the WDK extension, WiX 3.14 and Inno Setup 6.7.1, so it can build the DLL, run packetiser and clock simulations with USBPcap-derived fixtures, and smoke-test registration, but it has no USB or audio hardware; loopback tests need a self-hosted runner ([runner-images](https://github.com/actions/runner-images/tree/main/images/windows)).

## Gaps and negative findings

1. **No published latency number exists for any user-mode WinUSB isochronous audio driver, at any speed.** sd90 and AxeTwoDriver publish none, sd90's 3.38 ms is a synth response, and a GitHub code search for `WinUsb_WriteIsochPipeAsap` returned only headers and bindings.
2. **No evidence on whether the UR44 accepts WinUSB-style fixed-fill OUT packets.** The UR44's OUT `wMaxPacketSize` per alternate setting was not available to the researchers; the macOS engine parses it at runtime.
3. **No documented minimum scheduling lead on `usbxhci`/UCX** beyond Microsoft's +5-frame sample margin; no source on isochronous interrupt moderation or the typical value of `PredictedAccuracyInMicroSeconds`. The kernel-only `URB_FUNCTION_GET_ISOCH_PIPE_TRANSFER_PATH_DELAYS` query (Windows 10 1709+) has no documented WinUSB equivalent ([Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/usb/ns-usb-_urb_get_isoch_pipe_transfer_path_delays)).
4. **No Windows measurement of the original UR44 with a current driver**, no DAWbench data above 44.1 kHz, no Julian Krause Windows table in text form, and the SSL 1 figure (under 3.5 ms at 96 kHz/32 samples) was seen only in a search snippet.
5. **No official statement on self-signed WinUSB catalogs under Windows 11 24H2/25H2**, Memory Integrity or Smart App Control; USBPcap on Windows 11 is unconfirmed.
6. **No user-mode system-audio endpoint route found**; no measured latency for SysVAD-based bridges.
7. **No Steinberg answer on hand-written IASIO declarations or on loading third-party ASIO DLLs without an SDK agreement**; the official Steinberg download page and an official GitHub repository were not reachable, so SDK 2.3.4 text comes from the zip the Steinberg redirect delivered and from a third-party mirror.
8. **No Dutch case law or authoritative Dutch commentary read**; the "mandatory law" point rests on Directive Art. 8 plus one weak secondary source. The Dutch legislative history is only a scanned PDF.
9. **Open Windows packaging questions**: whether an individual can enrol in the Hardware Developer Program, whether attestation-signed drivers load under the new kernel trust policy (our inference is yes), whether UsbDk loads on 24H2 with Memory Integrity on, and whether libusbK.sys has a current signed build.
10. **No user-mode multi-process proof**: audio interfaces and the mixer interface in two processes through separate `MI_xx` WinUSB bindings, and a UAC1-style `SET_CUR` to an endpoint recipient through `WinUsb_ControlTransfer`, are both unverified.

## Recommendations: reuse versus write

1. **Reuse AxeTwoDriver's MIT crates as the starting skeleton; write the UR44 specifics.** Take `axetwo-usb` (descriptor parsing), `axetwo-win` (the `unsafe` WinUSB layer) and the `axetwo-stream` duplex loop, then audit them, since the code base is weeks old and AI-assisted. Add what neither project has: MMCSS, honest `getLatencies`, multi-rate alternate-setting handling for 44.1/48, 88.2/96, 176.4/192 kHz, six-channel 24-bit packing, drift servo and error recovery. Treat sd90 as a design reference only, because GPL-3.0 code cannot enter an MIT core.
2. **Make the packetisation test before building anything else.** If the UR44 tolerates WinUSB's fixed-fill distribution, the WinUSB route is viable. If it does not, the fallbacks are, in order: libusbK (per-packet `KISO_CONTEXT`; its signing and Windows 11 status must be researched), UsbDk (unmaintained, whole-device redirect), or a custom kernel driver with its attestation-signing cost. Do not commit to the ASIO adapter until this gate passes.
3. **Keep the architecture in-process.** An in-proc COM ASIO DLL owning the WinUSB handle (sd90's approach) avoids an extra IPC hop in the audio path, which matters because there is no latency to spare. The cost is single-client behaviour: a WinUSB handle opens once per devnode and ASIO is per-process. Multi-client needs a service or shared-memory arbitration (the irig-asio-driver idea) and is a later phase.
4. **Bind WinUSB per interface and keep mixer control separate.** Audio interfaces on one `MI_xx` WinUSB binding, the mixer/MIDI interface on another, each with its own `DeviceInterfaceGUID`. Use `nusb` for bulk SysEx and reuse the existing Rust mixer and urcontrol knowledge. First confirm which interface carries the SysEx (see the contradictions register).
5. **Treat the system-audio bridge as a separate, optional, kernel-signed product.** Ship ASIO first. If a bridge is wanted, derive from SysVAD or Virtual-Audio-Driver (MS-PL/MIT), feed it from a shared-memory ring slaved to the UR44 clock, and accept an EV certificate plus an eligible legal entity, or test-signing for early adopters. The zero-kernel fallback is to document routing through a third-party signed virtual cable, accepting its added latency.
6. **Do not decompile.** Use captures of the Yamaha driver, `getLatencies` logs per Latency Mode, and an A/B measurement of Yamaha's driver on the same machine. Revisit only for a specific unobservable item, with counsel.
7. **Set the expectation in the README.** Target parity with Yamaha's Windows driver (about 3.7 ms at 32 samples/44.1 kHz for the UR44C), not with the Mac figure, until measurements say otherwise.

## Qualification gates (run on the real UR44 before committing)

Each gate records host, OS build, CPU and xHCI vendor, port and hub topology, UR44 firmware, rate, buffer, queue depth, power plan and direct-monitor setting. Thresholds below are our proposals, not sourced.

| Gate | Measurement | Pass condition and consequence |
|---|---|---|
| G0 descriptors | Dump all alternate settings, OUT/IN `wMaxPacketSize`, `bInterval`, feedback endpoint presence, interface-to-`MI_xx` mapping on Windows; confirm high-speed enumeration directly on a root port and behind a hub | Settles the open questions in gaps 2 and 10 and the mixer-interface contradiction |
| G1 binding | INF-per-`MI_xx` WinUSB install with the AxeTwoDriver-style route, then the libwdi-style self-signed catalog, on clean Windows 11 25H2 with Memory Integrity and Smart App Control on; check precedence over Yamaha's INF and `usbaudio2.sys`; check revert | Installs without test-signing and survives a port change; otherwise evaluate Partner Center attestation of an INF-only package |
| G2 packetisation (make-or-break) | Send 1 ms OUT transfers of the exact implicit-feedback byte counts; capture with USBPcap and ETW to see how WinUSB distributes packets inside the frame; run a digital loopback with a known sample ramp at every rate for at least 10 minutes each, including the 44.1 kHz 5/6 pattern | Sample-exact, no underruns or glitches at all rates. A failure means fall back per recommendation 2 |
| G3 scheduling | Minimum viable start-frame lead (current frame + 1, 2, 3, 5) using explicit-frame writes and per-packet status; `ContinueStream` chain behaviour; IN completion jitter at 1 ms; `GetCurrentFrameNumberAndQpc` accuracy and generation changes; repeat on Intel and AMD xHCI and via a hub; test whether an in-flight registered IN buffer shows data before completion | Produces the latency-versus-queue-depth curve and the real floor; the buffer peek is a speculative bonus |
| G4 raw duplex baseline | Hours-long run at each rate with zero isochronous packet errors, packet counters, QPC-stamped completion log, with and without CPU load, sleep/wake, hot-unplug and rate change | No packet errors over at least 1 hour per rate; resync tested |
| G5 round trip | RTL Utility analog loopback (line out to line in) at 44.1, 48, 96 and 192 kHz and buffers 32 to 512; run the Yamaha V2.1.9 driver on the same PC for an A/B baseline; report minimum, worst case and non-buffer overhead; match the Mac buffer sizes for the normalised table | Overhead at or below about 2.2 ms (Yamaha UR44C level) justifies shipping; between 2.2 and 3 ms ships as "functional, not Mac-class"; the Mac's ~1.1 ms is not expected |
| G6 system stability | LatencyMon for at least 15 minutes under load; WPA context switches per second, DPC time for `winusb.sys`/`usbxhci.sys` against Yamaha's driver; EcoQoS opt-out; Intel hybrid CPU with the DAW in the background; Ultimate Performance versus Balanced power plans | No dropouts at the chosen default buffer; efficiency no worse than Yamaha's driver for the same workload |
| G7 ASIO host compatibility | In-process mini host (sd90's `asiotest` pattern), cpal harness, then Reaper, Cubase, Ableton and SONAR; outputs greater than zero, CLSID-as-IID, honest `getLatencies`, `outputReady` path, `ASIOGetSamplePosition` timestamps | RTL Utility reports no "suspect" flag; the hosts open, play and record |

## License implications

These are component-selection notes from the inspected declarations, not a completed distribution-licence audit.

**ASIO is the dominant constraint.** SDK 2.3.4 (dated 2025-10-15) is licensed under the Steinberg ASIO License "or alternatively under the terms of the General Public License (GPL) Version 3", and the proprietary route requires a Steinberg-signed agreement before publication and bars redistributing the SDK ([SDK 2.3.4](https://github.com/langlauf/asiosdk), mirror; same text in the [Steinberg zip](https://download.steinberg.net/sdk_downloads/ASIO-SDK_2.3.4_2025-10-15.zip)). The dual licence came with the OBS partnership ([Libre Arts](https://librearts.org/2025/11/steinberg-relicenses-vst3-and-asio/)); VST 3 went MIT but ASIO did not. The cleanest layout for an MIT project is the AxeTwoDriver split ([ATTRIBUTION.md](https://github.com/RamonWide/AxeTwoDriver/blob/main/ATTRIBUTION.md)): the USB engine, protocol, ring buffers and clock code stay MIT and know nothing about ASIO; a thin ASIO adapter DLL is GPL-3.0 under the SDK's GPLv3 option, published with source; and the README says the MIT core can be reused independently. The alternative is relicensing the whole project to GPLv3 (MIT code flows into GPLv3, not the reverse). Hand-writing the IASIO vtable, as AxeTwoDriver-DAW and sd90 do, is derived from the headers and should be treated as covered by the GPLv3 option; under the proprietary licence, §2.3 bars "re-working ... ASIO API calling sequences" ([Licensing Agreement](https://github.com/langlauf/asiosdk)), so a clean-room claim would be risky. cwASIO shows an SDK-free MIT reimplementation is being attempted, but there is no legal analysis and the trademark still applies. Microsoft's own pattern, in which MIT source "does not grant any license for the Steinberg ASIO SDK" and builders obtain it from Steinberg ([microsoft/low-latency-audio](https://github.com/microsoft/low-latency-audio)), together with FlexASIO's build-time download with a SHA1 pin, suggests never vendoring the SDK in the repository.

**Trademark.** The 2.3.4 Usage Guidelines allow "ASIO" in product names as "X for ASIO" with the logo nearby and the ® notice on first use, and forbid it in company names and variants such as "ASIOd"; the SDK README summarises the rule more strictly ([Usage Guidelines](https://github.com/langlauf/asiosdk)). AxeTwoDriver avoids the word entirely, reading the rule more strictly. A name such as "UR44 Low-Latency Driver for ASIO" is supportable on the guidelines as read, but confirm with Steinberg first (gate G9).

**Other components.** AxeTwoDriver core, urcontrol, nusb, windows-rs and cpal are permissive (MIT or Apache-2.0; retain notices, and Apache's notice and patent terms). sd90, AxeTwoDriver-DAW and Linux endpoint code are GPL and can inform the design but cannot be copied into the MIT core. libusb is LGPL-2.1; a Rust wrapper does not remove those obligations, and a direct WinUSB backend avoids the dependency. libwdi's library is LGPL-3.0-or-later and Zadig GPL, which matters only if embedded; calling `pnputil` with our own INF avoids the question, and our INF carries no libwdi code. SysVAD-derived miniport code is MS-PL (file-level copyleft; keep MS-PL files under MS-PL) and Virtual-Audio-Driver is MIT plus MS-PL. FastTrackC400-style repositories without a licence grant remain read-only, as in the macOS report. Yamaha binaries, firmware and decompiler output stay out of the repository; protocol facts and independently observed packet formats are different from copied code, and provenance of captures should be recorded.

**Signing and distribution.** The ASIO DLL and installer should be Authenticode-signed. A Dutch individual cannot use Microsoft Artifact Signing (individuals only in the US and Canada; EU organisations are eligible) ([Microsoft FAQ](https://learn.microsoft.com/azure/artifact-signing/faq)), so the options are an OV certificate or SignPath Foundation. SignPath requires an OSI licence "without commercial dual-licensing for all components" and no proprietary components ([SignPath terms](https://signpath.org/terms)); the ASIO SDK's proprietary second option might trigger an objection even when the GPLv3 route is used, so ask before applying. Neither route nor EV buys instant SmartScreen trust, which accumulates per certificate and file hash, so document "More info, Run anyway" and keep one signing identity across releases ([Microsoft](https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation)). A libwdi-style install also puts a locally generated certificate into the Root and TrustedPublisher stores, a user-visible security trade-off that favours the AxeTwoDriver-style `winusb.inf` selection or an attested INF-only package where possible.

## Conclusion

The macOS result does not transfer. On macOS the work was to remove delay that libusb added; on Windows the delay is built into the API, with 1 ms completion granularity, frame-granular scheduling and write calls that cannot shape packets. The surprising consequence is that the target should be recalibrated rather than abandoned: Yamaha's own kernel driver also sits at 2.2 ms of non-buffer overhead because kernel URBs at interval 1 are 1 ms units too, so a disciplined WinUSB design can plausibly land near Yamaha's Windows figure while the Mac driver keeps its 1.1 ms lead. Whether it lands there depends first on a single packetisation test, and then on queue depth and wake-up jitter that only the real UR44 can reveal.

The legal and licensing picture is simpler than it first appears. Black-box capture is protected by Dutch and EU law against the EULA, decompilation is both low-value and incompatible with publishing under MIT, and the October 2025 GPLv3 option for ASIO turns a former blocker into a layout decision: an MIT core and a GPL-3.0 adapter DLL. The costs that remain are mostly non-technical: a kernel bridge for system audio needs a signing identity that a Dutch individual may not be able to obtain, so ASIO-first, with the bridge optional, is the plan that matches both the evidence and the project's constraints.
