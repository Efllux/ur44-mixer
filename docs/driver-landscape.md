# UR44 user-space driver landscape

Research date: **2026-11-07**. Scope: existing software and technical evidence for a Full Security macOS UR44 driver, plus future Linux/Windows support. No project code was written, modified, built, installed, or tested during this research.

Evidence conventions: **P** means GitHub API `pushed_at` (repository activity, not necessarily a code change or release). **D** means a dated document/post. **V** means the URL/content was checked on 2026-11-07 but no reliable modification date was available. Repository licenses below combine metadata with selected license files/headers; “unknown” means no usable grant was established. Hardware success and performance figures are authors' reports, not independently reproduced results. Relevance: 5 = directly useful now; 4 = strong component/reference; 3 = future/adjacent; 2 = limited; 1 = background.

The device descriptors, existing Rust mixer and streaming spike, Yamaha latency measurements, and proposed architecture in the brief are treated as supplied project facts. This research does **not** establish that ≤2.2 ms analog round-trip latency is achievable.

## Summary: ten most valuable finds

1. **[QuadCaptureMac](https://github.com/louistissot/quad-capture-macos-silicon-driver)** — MIT; unusually close precedent: vendor-class, UAC1-like USB audio, IOUSBHost isochronous I/O, implicit feedback, hardware-derived HAL timestamps, and a control app. Start with its USB engine and timing design.
2. **[libusb Darwin backend](https://github.com/libusb/libusb/blob/master/libusb/os/darwin_usb.c) and [Apple's low-latency USB guidance](https://developer.apple.com/library/archive/documentation/DeviceDrivers/Conceptual/USBBook/USBOverview/USBOverview.html)** — explain a likely latency obstacle in the current spike: ordinary callbacks and a four-bus-frame scheduling lead. Use to decide when to replace the transport backend.
3. **[Equaliser](https://github.com/cvknage/equaliser)** — GPL-3.0; concrete BlackHole-derived HAL/app bridge, file-backed shared memory, custom properties, and installation lifecycle. Reuse the bridge design; replace its host-based clock for hardware streaming.
4. **[libASPL](https://github.com/gavv/libASPL)** — MIT; C++17 AudioServerPlugIn object/property framework with overridable timestamp implementation. Best established permissive alternative to maintaining a large BlackHole fork.
5. **[YunAudio](https://github.com/YuhuanStudio/YunAudio)** — Apache-2.0; real external-clock publication into a virtual driver's `GetZeroTimeStamp`, including lock telemetry. Useful for the helper-to-HAL clock contract even though its source clock comes through CoreAudio.
6. **[Linux snd-usb-audio](https://github.com/torvalds/linux/tree/master/sound/usb)** and **[Cyrus Harmon's UR44 patch](https://mailman.alsa-project.org/pipermail/alsa-devel/2014-March/074120.html)** — authoritative packet scheduling and original `0499:150e` interface mapping. Use as a behavior oracle and for a future Linux quirk, with file-specific GPL obligations if copying code.
7. **[PipeWire SPA DLL](https://github.com/PipeWire/pipewire/blob/master/spa/include/spa/utils/dll.h)** and **[Fons Adriaensen's DLL paper](https://kokkinizita.linuxaudio.org/papers/usingdll.pdf)** — compact MIT clock-recovery implementation plus the reasoning behind filtering scheduling jitter. Adapt for device-sample-count to host-time mapping.
8. **[line6-coreaudio](https://github.com/pbannykh/line6-coreaudio)** — GPL-2.0 declaration; the exact Rust libusb daemon → shared memory → C HAL topology. Valuable lifecycle and test-harness precedent, but input-only, large default buffering, and explicitly not device-clock-locked.
9. **[askoriy/urcontrol](https://github.com/askoriy/urcontrol)** — MIT; UR44C SysEx library, parameter knowledge, and a Wireshark Lua dissector. Use for protocol cross-checking and sibling-device expansion, not as proof of identical UR44 registers.
10. **[FastTrackC400](https://github.com/ruslanvakhitov/maudio_fast_track_c400)** — close full-duplex IOUSBLib/HAL implementation with implicit feedback and smoothed clock anchors. Strong technical reference, but **no detected license**: do not copy its code without a grant.

### The transport result that matters

At the inspected [Darwin source revision](https://github.com/libusb/libusb/blob/d5c4a631eeb0cc238b28f4e0c0c9bc16a0615ab9/libusb/os/darwin_usb.c), submission reads `GetBusFrameNumber`, adds four frames, and chooses the maximum of that value and the previous request's endpoint cursor. High-speed packet duration is separately divided by eight. Thus the four-frame lead is approximately **4 ms**, not four 125 µs microframes. This is a code-derived inference about newly submitted output data, not a measured round-trip result. It makes a conventional fill-before-submit libusb path a poor fit for ≤2.2 ms RTL.

[QuadCaptureMac's design document](https://github.com/louistissot/quad-capture-macos-silicon-driver/blob/main/docs/PROTOCOL.md) describes a different mechanism: long-lived queued transfers, playback written near its bus deadline, and capture scanned after individual microframes. Its [engine](https://github.com/louistissot/quad-capture-macos-silicon-driver/blob/main/src/engine/qc_engine.m) uses IOUSBHost transaction lists and a real-time scanning thread. This decouples **queue duration** from **audio age**. It is the strongest lead found for a lower-latency experiment, but buffer visibility, safe write deadlines, cancellation and OS-version behavior must be verified on the UR44. The project's reported safety offsets are not a demonstrated ≤2.2 ms analog RTL.

Availability discrepancy: that engine gates `currentMicroframeWithTime:error:` at macOS 26, while [Apple's current API documentation](https://developer.apple.com/documentation/iousbhost/iousbhostobject/currentmicroframewithtime%3Aerror%3A) metadata lists macOS 10.15. Resolve this against the target SDK and actual runtime; do not copy the example's version assumption as an established API requirement.

### What to transfer into the UR44 design

- **Separate three clocks/quantities:** observed device sample position, USB service position, and host monotonic time. Use a filtered mapping for timestamps. Do not timestamp audio solely with callback arrival time.
- **Separate packet matching from rate estimation:** [Linux's endpoint engine](https://github.com/torvalds/linux/blob/master/sound/usb/endpoint.c) explicitly takes implicit-feedback packet sizes from its sync source. A slowly filtered average is useful for host-time conversion, but does not automatically reproduce the device's per-packet pattern.
- Keep the capture endpoint active while playback needs its implicit feedback. Match actual service intervals and convert packet bytes to complete sample frames with the correct channel stride.
- Publish a coherent clock tuple: generation/seed, device frame count, corresponding host time, estimated ticks/frame and running/valid status. Rate changes, unplug/reconnect and discontinuous resynchronization need explicit lifecycle handling. This is a recommended contract, not a library discovered ready-made.
- Keep resampling as a fallback for a genuinely separate clock domain, such as another output device. Making the HAL facade follow the same UR44 crystal should avoid permanent ASRC in the main path. Validate that with drift and sample-integrity measurements.
- Budget USB scheduling lead, input delivery delay, HAL buffers/safety offsets, helper bridging, and converter/DSP latency separately. Verify UR44 endpoint `bInterval` and actual packet cadence: a high-speed link alone does not prove a 125 µs audio service interval or an analog round-trip latency.

A matching **UR44 vendor PID `0x150e` entry was not found** in those inspected current files. Harmon's 2014 mail remains useful, but must not be described as a current upstream UR44 vendor-mode implementation. CC support and UCM profiles are separate evidence. [Quirk table](https://github.com/torvalds/linux/blob/master/sound/usb/quirks-table.h), [flags](https://github.com/torvalds/linux/blob/master/sound/usb/quirks.c), [implicit matching](https://github.com/torvalds/linux/blob/master/sound/usb/implicit.c).

Shared REV-X/channel-strip branding is insufficient evidence. Treat each as a new model with descriptors/captures to verify.

## Gaps and negative findings

1. **No public, independently measured ≤2.2 ms analog RTL UR44 user-space macOS implementation found.** Similar drivers prove architectural plausibility. Their README claims, queue sizes and timestamp tests do not establish this target.
2. **No generic, mature, turnkey macOS user-space UAC1/UAC2 full-duplex host library found.** libuac is partial UAC1 capture; libmaru is old Linux-oriented playback; the strongest current macOS examples are device-specific.
3. **No drop-in Rust combination of HAL plug-in + full-duplex isochronous USB + device-clock recovery found.** tympan-aspl and objc2 bindings are useful pieces; nusb currently does not supply the missing audio transport.

## Recommendations: reuse versus write

### Immediate architecture choices

1. **Keep the working Rust spike as the correctness baseline.** Preserve packet/error/clock observations before changing transport. A clean tone establishes useful USB access; it does not establish duplex stability or tight RTL.
2. **Run the transport latency experiment before committing to a large HAL fork.** Evaluate an IOUSBHost backend using QuadCaptureMac's engine/design as the primary permissive reference and `objc2-io-usb-host` for Rust bindings. Compare callback delivery against per-microframe visibility. Keep libusb as a portable baseline/fallback.
3. **Retain the proposed helper/HAL separation for the product, provisionally.** line6-coreaudio validates the structure and restart handling. The lowest-latency examples put USB inside the HAL driver host, so benchmark whether helper scheduling and cross-process handoff matter at the target. Move USB into the plug-in only if measured benefit justifies coupling USB lifecycle to the audio host.
4. **Choose one HAL base deliberately.** With a GPL-3 driver, adapt BlackHole/Equaliser. For a permissive codebase, prefer libASPL or Apple's minimal sample, with tympan-aspl as a Rust candidate needing more qualification. Don't combine several HAL frameworks to avoid selecting one.
5. **Write the UR44-specific transport state machine.** Enumeration/mode matching, exact altsettings, UAC1 endpoint sample-rate control, 6×24-bit packing, implicit-feedback counts, USB errors, rate change, suspend/reconnect, and mixer/MIDI ownership still need device-specific implementation.
6. **Write the shared-memory ABI and clock contract for this hardware.** Reuse patterns, not an EQ app's assumptions. Include two directions, bounded rings, coherent counters/clock snapshots, format/generation validation, stale-helper detection, and predictable under/overrun recovery. Use Mach/XPC or HAL properties for control; keep synchronous RPC out of the audio path.
7. **Adapt the MIT SPA DLL if needed.** Keep raw capture packet counts for feedback, and filter device-position/host-time observations separately. Validate timestamp monotonicity, restart seeds and long-run drift. Do not solve an incorrect virtual clock by continually dropping/duplicating samples.
8. **Keep the existing mixer app and protocol work.** Import only useful MIT urcontrol knowledge/dissector improvements. Add model/capability definitions for future siblings; do not replace the already more complete UR44 parameter table with a UR44C-oriented table.

### Qualification gates

- Establish a timestamped raw-USB duplex baseline, then the HAL path, then analog line-output → line-input RTL. Record host/OS, port/hub topology, firmware, rate, buffer, USB queue configuration and direct-monitor setting.
- Measure distribution and worst observed callback lateness, underruns/resyncs and long-run drift, not just minimum RTL. Include output-only clients, several HAL clients, sleep/wake, unplugging, rate changes, and CPU load.
- Check all six host playback channels by device routing/meters. Outputs 5/6 feed the FX bus; do not present them as two extra independent analog sockets.
- Use standalone engine and HAL-conformance tools before installing; use soundcheck/JACK tooling or RTL Utility for an independent loopback check. Keep DAW latency reporting/safety offsets honest.
- For Linux later, upstream or maintain the minimal vendor-interface/implicit-feedback quirk first, then the UCM channel layout. Reuse kernel audio where available; a user-space USB engine is not automatically the best Linux integration.
- For Windows later, separately evaluate raw transport access, normal WASAPI exposure and an ASIO facade. FlexASIO/iRig do not solve vendor USB transport; Microsoft provides a more substantial kernel/UAC2 reference, with a different scope.

### License implications

These are component-selection notes based on the inspected project declarations, not a completed distribution-license audit.

- **MIT / BSD / Apache path:** libASPL, QuadCaptureMac, urcontrol, SPA `dll.h`, relevant FreeBSD code and objc2 bindings make a credible permissive foundation. Retain copyright/license notices; Apache components also have notice/patent provisions. Apple sample packages must retain their own notices.
- **BlackHole / Equaliser:** copying/modifying their GPL-3 driver code means distributing the derivative with applicable GPL source/license obligations. A separate helper process is not by itself proof that every connected component is legally independent; design and provenance matter. BlackHole's current license also distinguishes source from official binaries/branding: build and brand this project's driver appropriately.
- **GPL-2 versus GPL-3:** do not assume line6-coreaudio or Background Music can simply be pasted into a GPL-3 fork. A GPL-2 text in `LICENSE` does not prove an “or later” election. Check each copied file's grant or obtain permission. In contrast the inspected Linux endpoint/implicit files explicitly say GPL-2.0-or-later. See the [FSF's version compatibility explanation](https://www.gnu.org/licenses/gpl-faq.html#v2v3Compatibility).
- **AGPL:** yourc-tools is useful research but adds AGPL conditions if incorporated; prefer existing MIT urcontrol or original UR44 code when equivalent.
- **libusb LGPL:** Rust wrappers do not remove libusb's obligations. Preserve notices/source requirements and satisfy the selected static/dynamic linking and replacement/relinking conditions. A new IOUSBHost backend can avoid that dependency in the macOS streaming path while retaining it elsewhere. See the [FSF's linking explanation](https://www.gnu.org/licenses/gpl-faq.html#LGPLStaticVsDynamic).
- **No grant means no copying:** C400 is a highly relevant read-only reference until licensing is clarified. Treat JackRouter and miscellaneous forum snippets similarly where no grant is established.
- **ASIO:** pin the chosen SDK and its proprietary or GPLv3 license route. Microsoft's MIT repository does not sublicense Steinberg's SDK. Keep third-party SDK code out of a permissive relicensing assumption.
- **Protocol facts versus implementation:** an endpoint map, observed packet format or independently documented behavior is different from copying source code. Maintain provenance for borrowed implementation and for original UR44 captures; don't import manufacturer binaries into the source tree.

The most valuable next investigation is therefore **IOUSBHost timing on the actual UR44**, followed by a device-driven HAL clock. Existing work provides enough scaffolding to avoid rebuilding those interfaces blindly, but the latency claim still needs a hardware measurement.
